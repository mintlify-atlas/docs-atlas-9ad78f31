---
title: "Get started with zEnv"
description: "Set your credentials, store your first encrypted secret, and fetch it back using the CLI and the TypeScript SDK — all in a few minutes."
---

This guide walks you through the full cycle: configuring credentials, storing a secret via the CLI, and loading it in a TypeScript application with the SDK. All encryption happens on your machine before anything touches the network.

<Warning>
  zEnv is pre-alpha software. APIs will break without notice and no security audit has been completed. Do not use it to store secrets you depend on in production.
</Warning>

<Steps>
  <Step title="Start the API server">
    zEnv requires a running API server backed by PostgreSQL and Redis. Start the local dev stack with Docker Compose, then run migrations and build the binaries.

    ```bash
    # Start Postgres + Redis
    make dev-up

    # Run database migrations
    make migrate

    # Build the CLI and API server binaries
    make build
    ```

    Once the build completes, start the API server:

    ```bash
    DATABASE_URL="postgres://zenv:zenv_dev@localhost:5434/zenv?sslmode=disable" \
    REDIS_URL="redis://localhost:6379" \
    ./bin/zenv-api
    ```

    The server listens on port `8080` by default.
  </Step>

  <Step title="Set your credentials">
    The CLI and SDK both authenticate using a service token and a project key. Set these as environment variables — the project key never leaves your machine.

    ```bash
    export ZENV_TOKEN=ze_development_...      # Service token (from the dashboard or API)
    export ZENV_PROJECT_KEY=...               # Your project's Vault Key — never sent to server
    export ZENV_PROJECT=<project-id>          # Project UUID
    export ZENV_ENV=development               # Target environment
    ```

    Alternatively, commit a `.zenv` file to your repository so the whole team inherits the project context automatically:

    ```ini
    # .zenv — safe to commit, contains no secrets
    project=ecommerce-backend
    env=development
    ```

    The CLI resolves context in this order: explicit flags → `.zenv` file → environment variables → default.
  </Step>

  <Step title="Store a secret via the CLI">
    Encrypt a secret client-side and store it in the vault. The CLI uses the Go Amnesia engine natively — no WASM, no runtime dependency.

    ```bash
    ./bin/zenv secrets set DATABASE_URL "postgres://prod:secret@db.internal/myapp"
    ```

    The value is encrypted locally before the request is sent. The server receives only ciphertext.

    To confirm it was stored:

    ```bash
    ./bin/zenv secrets get DATABASE_URL
    # postgres://prod:secret@db.internal/myapp
    ```

    List all secrets in the current environment (metadata only — values are never returned by list):

    ```bash
    ./bin/zenv secrets list
    ```
  </Step>

  <Step title="Inject secrets into a process">
    Use `zenv run` to decrypt all secrets and inject them as environment variables into any command. This works with any language or runtime.

    ```bash
    ./bin/zenv run -- node server.js
    ./bin/zenv run -- python app.py
    ```

    For CI validation before a deployment, `zenv check` exits with code `1` if any required secrets are missing:

    ```bash
    ./bin/zenv check DATABASE_URL STRIPE_KEY JWT_SECRET --env production
    ```
  </Step>

  <Step title="Install the TypeScript SDK">
    For server-side TypeScript applications, install `@zenv/sdk`:

    ```bash
    pnpm add @zenv/sdk
    ```

    <Note>
      The SDK throws a hard error if `window` is defined. `ZENV_TOKEN` and `ZENV_PROJECT_KEY` are server credentials — they must never reach the browser.
    </Note>
  </Step>

  <Step title="Load secrets with the SDK">
    Create a vault client, define a Zod schema, and call `vault.load()`. The SDK fetches the ciphertext, decrypts it locally using `@zenv/amnesia`, and validates the result against your schema.

    ```typescript
    import { zenv } from "@zenv/sdk";
    import { z } from "zod";

    const vault = zenv({
      token: process.env.ZENV_TOKEN!,
      projectKey: process.env.ZENV_PROJECT_KEY!,
      projectId: process.env.ZENV_PROJECT_ID!,
      environment: process.env.NODE_ENV,
      schema: z.object({
        STRIPE_API_KEY: z.string().min(1),
        DATABASE_URL: z.string().url(),
        PORT: z.string().transform(Number),
      }),
    });

    const secrets = await vault.load();
    // secrets.STRIPE_API_KEY → string
    // secrets.DATABASE_URL   → string
    // secrets.PORT           → number (transformed by schema)
    ```

    You can also fetch a single secret or write one back:

    ```typescript
    // Fetch a single secret
    const apiKey = await vault.get("STRIPE_API_KEY");

    // Write a secret (encrypts locally, stores ciphertext)
    await vault.set("DATABASE_URL", "postgres://prod:secret@db/myapp");

    // Delete a secret
    await vault.delete("OLD_API_KEY");
    ```
  </Step>

  <Step title="Export secrets to a .env file">
    Pull all secrets for an environment into a local `.env` file using the CLI:

    ```bash
    # Write to .env.local (default)
    ./bin/zenv env pull

    # Write to a custom file
    ./bin/zenv env pull -o .env.production

    # Print to stdout
    ./bin/zenv env pull -o -
    ```

    To compare two environments:

    ```bash
    ./bin/zenv env diff development production
    ```
  </Step>
</Steps>
